# log-food skill: Claude logs meals into the app through the backup's inbox

- **Date:** 2026-10-27
- **Status:** accepted; pushing through the inbox superseded by [log-food-sync](2026-10-29-log-food-sync.md)
- **Instructions:** [`docs/instructions/design.md`](../instructions/design.md) (Config screen: backup)
- **Builds on:** [backup](2026-10-27-backup.md), [import-merge](2026-10-27-import-merge.md)

## Context

User in chat: "I want to be able to dump a bunch of logs to you, and I want you to be able to figure out the
internals yourself. I want you to ask as many questions as you need in order to provide the best estimate. And I want
you to push it automatically to the website (using the backup key). Defer use of OFF unless strictly needed. I want
you to use error margins wide enough so that everything stays correct".

## Decision

- **An inbox per key**, beside the backup (server: `GET/PUT/DELETE /backup/<key>/inbox`, one blob, compare-and-swap
  on its version, same size cap; a key change drops it, after the app takes it in). Claude adds batches to it; the
  app merges each batch with the import's merge (`mergeTables`) and clears the inbox: soon after opening, every 15
  minutes, and whenever the app comes back to the foreground. The Backup screen says how many consumptions came in.
  - Not pushing a whole new backup: the phone's next upload would conflict, and settling it by merging would bring
    back what the phone deleted meanwhile. The inbox only ever adds.
  - Merging is idempotent (repeats are skipped), so a batch taken in twice (the DELETE lost to a race) adds nothing.
- **Shared crypto**: `app/src/backup-crypto.js` (keys, encryption, signed requests; no imports, web APIs only) is used
  by the app's `backup.js` and by Node.
- **The skill**: `.claude/skills/log-food/` (SKILL.md + `scripts/food.mjs`). The tool pulls and decrypts the backup
  (`.secrets/`, git- and docker-ignored), searches own foods and the bundled CIQUAL and USDA tables, and turns a
  compact batch (user, new foods, consumptions with `at`, `food`, `amount`, `delta`, `unit`, `entryError`,
  optional `group`) into the app's export format. It checks it (user exists, foods resolve, units convert as in
  `calc.js`, times carry a UTC offset, nutrient keys are the app's), prints each entry with nominal kcal, and adds it
  to the inbox.
  - Own foods are copied exactly into the batch, so the merge recognises them; new foods get `database: Claude
    estimate`. Group ids follow from the group's name and first time, so a batch always builds the same rows.
- **Error margins** (SKILL.md): `delta` is a hard bound (the app reads it as uniform), chosen as the half-width of
  the range the amount surely lies in, by how it was measured (weighed: the scale; counted: ±15–25%; eyeballed:
  ±40–60%; vague: up to ±100%). `entryError` from 0.1 (close reference match) to 0.3–0.5 (unknown recipe, estimated
  food), on top of the category's sampling CV. Hidden fats and sugars are logged with ranges reaching 0, never left
  out.
- **OFF** only for a named branded product that differs a lot from any generic food.
- The skill asks with AskUserQuestion in as many rounds as needed, skipping what history, memory or a negligible
  effect answers; it pushes without a confirmation step, then shows what it logged.

## Alternatives considered

- **Claude edits the full backup** (pull, merge, push): conflicts with the phone and resurrects deletions (above).
- **A separate API key for Claude**: more server code for the same trust; the user asked for the backup key.
- **Logging dishes as new recipe foods**: one-off dishes would pile up as foods; grouped consumptions keep each
  ingredient's error and leave the food list alone. Recurring dishes the user already has stay their own recipes.

## How it was checked

- `npm run build`. Local server and `vite preview`, headless Chromium as the phone, the tool against it
  (`FOOD_TRACKER_URL`): the phone imports own foods (an egg, a soup recipe) and starts a backup; `secret`, `pull`,
  `find`, `push --dry-run`, `push`, `inbox`. The phone took the batch in by itself: the egg and soup recognised as
  its own (not duplicated), the new food added, the group kept, the reference food computed; the inbox emptied;
  pushing the same batch again added nothing.
- The check caught a test entry in grams of a recipe that has no unit (the app counts it in portions); it now
  refuses units the app couldn't convert, recipes included.
- Not checked: against the production server (needs this server and web image deployed), and the skill run on a
  real dump.
