# Targets screen

- **Date:** 2026-10-15
- **Status:** accepted
- **Instructions:** [`docs/instructions/design.md`](../instructions/design.md) (Homescreen: "Button: targets"; "Targets screen")

## Context
`design.md` now has a Targets screen: "List targets, latest first. A target consists of the fields that the user
defines, limited to energy and any nutrients. It's timestamped, so that it's only valid from its timestamp until the
next target's." Until now, four fixed daily targets lived in Config (my own earlier addition).

## Decisions
- **Storage:** new `targets` table `{validFrom (ISO), values: {nutrientKey: number}}`. Only the nutrients the user
  set are stored (no NaN placeholders). Energy is one of the nutrient keys.
- **Values are per day.** Weekly and monthly targets are the sum, over each day in the window, of the target valid
  that day.
- **Which target applies to a day:** the latest whose `validFrom` is before that logical day *ends*. A target created
  mid-day counts for that whole day; otherwise a target set "now" would only show from tomorrow, which looks broken.
- **Days with no target for a nutrient** add nothing. So a nutrient added to targets mid-week is compared, for that
  week, only against the days it covers. Flagged below.
- **Dashboard:** Calories/Protein/Carbs/Fat are always shown, and every other nutrient that has a target in the window
  gets its own row (e.g. Fibers). Status colours are unchanged (<90 % ↓, 90–110 % ✓, >110 % ↑).
- **Targets screen:** cards newest first: "From <date>", "until <next>", values, "per day", plus an `active` or
  `upcoming` tag. "+ add target" opens a bottom sheet pre-filled with the latest target's values and valid-from = now.
  Nutrient rows have × to remove, and new ones come from the same autocomplete (`NutrientAdder`, moved to
  `components.jsx`), with the cursor jumping to the new value field.
- **Config** keeps only the day-start offset, as `design.md` lists.

## Migration
- Dexie v7: the old `config.targets` become one target, valid from the first consumption's time (or now if there
  are none), so history keeps being compared against it. `targets` is then removed from config.
- Exports are now `version: 4` and include `targets`. Importing older files performs the same conversion.

## Verification
Headless Chromium: a v6 DB with config targets (2000 kcal, 120 g protein) migrated into one target. Added a target from
now (2500 kcal, 120 g protein, 30 g fibers via autocomplete + Enter → value). The list shows both with "until", and
the newest is `active`. Daily shows a Fibers row (33 % of 30). Weekly (Mon–Sun, new target from Thu): energy target
3×2000 + 4×2500 = 16000, protein 840, fibers 4×30 = 120. An export/import round trip keeps 2 targets. No errors.

## Update: min/max ranges, dashboard rows, progress bars
User request: "targets to have a min and a max (both optional)"; "Anything that gets a target written should be in the
dashboard"; "a progress bar … min at 50% (if no max), the max at 80% otherwise (and min accordingly), and it just
clips if you exceed the max".

- **Values** are now `{nutrientKey: {min?, max?}}`. Either bound can be left empty, but not both. min > max is refused.
- **Migration:** old single values v become `{min: 0.9v, max: 1.1v}` (Dexie v8 via `targetToRange()`, and imports of
  export version < 5). That keeps exactly what the dashboard used to treat as "on target" (90–110 %). Exports are now
  `version: 5`.
- **Window sums:** min and max are each summed over the days that set them (same caveat as before).
- **Dashboard rows:** core four + **every nutrient mentioned in any target** (any time, not just this window). A row
  without a target for the current window just has no bar.
- **Progress bar** (`targetBar()`): with a max, max = 80 % of the width and min proportionally (min/max × 80 %). With
  only a min, min = 50 %. The fill clips at 100 %, and thin marks show min/max. Colour/status: below min = amber ↓,
  above max = red ↑, otherwise green ✓. Label: "1800–2200 kcal", "≥ 100 g" or "≤ 2300 mg". A max of 0 puts the
  mark at 0 and anything above it shows full red.
- **Targets editor:** min and max columns with × per row. The cursor goes to "min" after adding a nutrient. Cards show
  ranges.

Verified (headless Chromium): old {2000, 120} → 1800–2200 / 108–132; bars: calories 384 vs 1800–2200 → fill 14 %, marks
65 %/80 %; protein 13 vs ≥100 → fill 6.6 %, mark 50 %; caffeine 435 vs ≤400 → 87 %, red; sodium with no intake → ✓.
No errors.

- Follow-up ("Use square brackets plus a slight highlight of each region"): min/max marks are now bracket shapes,
  **[** at the min and **]** at the max, drawn slightly taller than the bar. The track is tinted per region at
  18 % opacity: amber below the min, green within range, red above the max. With only a min, everything after the [
  is green; with only a max, everything before the ] is green. The fill sits on top in the status colour.

- Follow-up ("Fill in with blank space whatever doesn't have targets, so that everything is equally spaced"): rows
  without a target in the window render an invisible placeholder (`.dash-target.placeholder`, `visibility: hidden`)
  with the same bar + label structure, so every dashboard row has the same height (verified: all rows 103 px).

- Follow-up ("Enframe the space for every different element in the dashboard, with a slightly clearer tone"): each
  dashboard row is its own rounded frame (20 px radius, `--panel-2` = #232a33, a touch lighter than the dashboard's
  `--panel`), 8 px apart inside the dashboard card. Rows remain equal height (111 px).

- **Gauges (was an experiment, now a Config option)** — "Let's try an nx2 grid and a gauge bar. Similar aesthetics":
  restore point committed first (`2f54e4a`). The dashboard is now a 2-column grid of equal tiles (`--panel-2` frames):
  label, a semicircle SVG `Gauge`, the big value inside the arc, "unit ±Δ", and the range label. The gauge uses the same
  `targetBar()` scale, the same tinted regions and status-coloured fill, and the [ ] brackets bent along the arc (caps
  opening towards the range). Regions are drawn with square ends that overshoot, then masked to the round-ended track
  (a plain round-capped track left dark dots at the ends). Tiles without a target keep the gauge's space (hidden) so
  all tiles match (174×167 px on a Pixel 7).
- Follow-up ("For the gauge, don't use square brackets. Use a simple line. Add a config toggle between the two"): gauge
  min/max markers are plain radial lines (`tick()`) slightly longer than the arc's width. The bars keep their [ ].
  Config gets a **Dashboard style** two-way toggle (Gauges | Bars), stored as `config.dashboard`, default `'gauges'`
  (the user's latest choice). Home renders `GaugeTile`s in a 2-column grid or `BarRow`s in one column. Both share
  `targetBar()` and a `RangeLine`. This adds a setting `design.md`'s Config section doesn't list.

Note: `design.md` still describes a target as plain values and doesn't mention the bar. Proposed wording for the
user, not applied because instructions are human-only.
