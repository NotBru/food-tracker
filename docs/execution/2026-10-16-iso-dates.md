# Dates shown as YYYY-MM-DD everywhere

- **Date:** 2026-10-16
- **Status:** accepted
- **Instructions:** [`docs/instructions/design.md`](../instructions/design.md) (all screens)

## Context

User: "Dates should follow YYYY-MM-DD format everywhere."
- Dates were shown in the browser's locale: "Thu, Oct 15, 2026", "10-12 → 10-18", "October 2026",
  "1/2/26, 7:05 AM".
- The native `datetime-local` inputs also show the phone's locale format. Pages can't change that.

## Decision

### Displayed dates (helpers in `time.js`)
| Where | Now |
|---|---|
| Home, daily | `Today · Fri 2026-10-16` |
| Home, weekly | `This week · 2026-10-12 → 2026-10-18` |
| Home, monthly | `This month · 2026-10` |
| Consumptions day navigator | `Fri 2026-10-16` |
| Consumption list time | `12:30` (24 h; was locale "12:30 PM") |
| Concoction label ("made …") | `2026-10-14 18:05` |
| Targets "From / until" | `2026-01-02 07:05` |

- `prettyDay` keeps a short weekday in front of the date, because it helps when browsing days. That is an
  addition; the date itself is YYYY-MM-DD.
- `formatDateTime` gives "YYYY-MM-DD HH:MM", with 24-hour times so the whole stamp is locale-free.

### Date/time inputs: `DateTimeInput` (`components.jsx`)
- It replaces the three `datetime-local` inputs:
  - the consumption's date and time;
  - the target's "valid from";
  - the food's "made at".
- It is a text field showing `YYYY-MM-DD HH:MM`.
  - It only reports valid dates; an impossible one like 2026-02-30 is rejected. The field gets a red border
    until the text is valid.
  - On blur it falls back to the last valid value.
- A 📅 button next to it opens the native picker (a hidden `datetime-local`), as the Consumptions day picker
  already did.
- Stored values are unchanged (ISO / "YYYY-MM-DDTHH:MM").

### Already compliant
- The export filename (`food-tracker-YYYY-MM-DD_HH-MM-SS.json`).

## Alternatives considered

- **Keep the native inputs.** Their display follows the phone's locale (e.g. MM/DD/YYYY), which goes against
  the instruction.
- **Drop the weekday.** It would be stricter, but the weekday helps when browsing days. It is easy to remove if
  unwanted.

## Verification

Headless Chromium with locale en-US:
- All the strings in the table above render as listed.
- The editor field shows "2026-10-16 12:30". Partial input and "2026-02-30 10:00" are marked invalid.
- Typing "2026-10-16 09:15" and saving stored 09:15 local time.
- No console errors.
