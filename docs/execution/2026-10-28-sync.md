# Backup sync: three-way merge against the last synced copy; random ids; sync icon

- **Date:** 2026-10-28
- **Status:** accepted
- **Instructions:** [`docs/instructions/design.md`](../instructions/design.md) (Homescreen, Config screen: Backup)

## Context

The backup only uploaded: a phone's changes never reached the laptop, and two devices on one secret overwrote each
other (a 409 stopped uploads until the user picked a side). The user asked for: keep the last synced backup and the
local changes; if the backup moved, merge its changes with the local ones and upload, bound to the old version
(another device in between: merge again); a "synced" field on top (grey off, red differs, green in sync). Then,
after a critique round:

- Local changes are not stored as a separate delta that's cleared on upload (edits made mid-upload would be lost):
  they're computed as the data minus the base.
- Random ids (user's pick over renumbering on rebase).
- The server's version (a hash, already compare-and-swap) is the token, not device timestamps.
- Conflicts: the user picks, from the Backup screen. A violet icon, labelled "Merge conflict" unless turned off.
- Config syncs, completely; the same secret means the same users. Restore and Replace warn.
- First sync of two devices that never synced: like an import's Merge (union).
- Red is failing, yellow waiting; sync a few seconds after edits stop; icon with hover text.

## Decision

- **Ids** (`db.js`): v16 / export format 8. Rows get `makeId()`: base-36 time (9 chars) + 8 random chars, so they
  sort by creation like the old numbers did (`byId` replaces `a.id - b.id`). Migration (`randomIds`, for the database
  and for any import with numeric ids) maps old number n to `makeId(n)`, which sorts before every new id; references
  follow (consumptions, components, targets, body measurements, the selected user). A Dexie `creating` hook gives new
  rows their id, so no screen had to change beyond reading route ids as strings. `mergeTables` keeps an import's
  ids unless taken here.
- **Base** (`sync` table, outside the export): the backup's text and server version as this device last uploaded or
  merged it. Local changes = rows differing from the base (`sync.js changes`), by id, key order ignored.
- **Round** (`backup.js syncRound`): download. Backup moved since the base → `merge(base, local, backup)` per row:
  changed on one side → that side; same change on both → fine; different (delete counts) → conflict, this device's
  row stays meanwhile. Applied in one transaction with the new base, so edits made meanwhile aren't overwritten.
  Then upload with `prev` = base version if anything differs; 409 → another round (up to 5).
  - No base yet (first sync, including every device already backing up): import-Merge the backup, then upload.
  - Nothing on the server: upload (the user's "push the local backup first"; a base can't be *newer* than the
    server's copy, only missing from it).
  - Backup from an older app (format < 8) while a base exists, or a newer one: stop with an error saying which
    device to update; merging across the id change would duplicate everything.
- **Still used, still there:** a row deleted on one side but referenced by the other's (a new consumption of a
  deleted food, a user deleted with their consumptions while another device logged one) is kept, not a conflict.
- **Selected user** (`config.currentUser`) stays per device: it's which user this device shows, not data.
- **Conflicts** wait in the `sync` table; syncing stops until each is picked ("Keep this device's" / "Keep the other
  device's", with the differing fields or "deleted on …"). Then it syncs again.
- **When:** 2 s after opening, 3 s after the last change (Dexie hooks; the sync's own writes are quiet), every
  15 minutes, on hiding and 1 s after showing the app. One at a time; asked meanwhile, once more after.
- **Icon** (homescreen, left of Config): a cloud; ✓ green synced, … yellow waiting (changes here not uploaded, or
  never synced), ! red failing (the error in the hover text and on the Backup screen), ⇄ violet conflict, struck
  grey off. Colour plus glyph, so it doesn't rely on colour alone. Tap → Backup. The "Merge conflict" label is
  switched on the Backup screen (per device, localStorage).
- **Backup screen:** status line, conflicts, "Sync now" (was "Back up now"); Restore warns unsynced changes are
  lost; Change the secret syncs first and refuses with conflicts pending. Import's Replace warns it replaces the
  data on every synced device.
- The log-food skill's new foods took `max(id) + 1000`; with string ids that's NaN, so it takes the max of the
  numeric ones (the app gives them random ids on the way in).

## Alternatives considered

- **Delta stored and zeroed on upload** (user's first sketch): loses edits made while uploading; every write site
  would have to record into it.
- **Renumbering this device's new rows on rebase**: smaller change, but an open screen loses a renumbered row.
- **Last edit wins per row (`updatedAt`)**: the user preferred picking; conflicts should be rare.
- **Field-level merge** (different fields of one row both kept): fewer conflicts, more to explain; row-level for now.
- **"Syncing" as yellow**: every 15-minute check would flicker; yellow means changes waiting.

## Consequences

- Every device's first sync after this update is a union, as an import's Merge: deletions made on one device
  before it may come back once.
- Exports are format 8; older apps importing them would get string ids they don't expect (they ignore format).
- Old links to `#/foods/12` or `#/consumptions/12` stop resolving (ids changed).
- A future format bump must migrate the base like any import (`tablesOf` does via `readImport`); one that changes
  ids again would need the base handled like v8's.
- Green means "matched the backup at the last check"; another device's change shows up at the next sync.

## How it was checked

`npm run build`. Local backup server and `vite preview`; Playwright 1.55 with two persistent Chromium profiles,
starting on the previous build (backup started on A, restored on B, a consumption added on B and uploaded), then on
this one:
- Migration: string ids; components and the selected user follow.
- First syncs: A gets B's consumption (4, foods not duplicated); B then A: identical data.
- Adding through the app: icon yellow, then green by itself a few seconds later; B takes it in.
- Deleting on B: gone on A, and stays gone.
- Different rows edited on each: both kept.
- Same row edited on both: conflict on B, violet "Merge conflict" icon, both amounts listed; keeping the other's.
- Deleted on A, edited on B: conflict ("Deleted on the other device"); keeping B's brings it back to A.
- A deletes a food while B logs it: the food stays on both, no conflict.
- Both syncing at once: both changes everywhere (the 409 path).
- Offline: red, hover text with the reason; back online: green.
- Replace's confirmation mentions every synced device. Phone width: icon and label fit beside Config and the user.
After each: both devices' tables equal (selected user aside).
