# Open Food Facts: our own copy on the server

- **Date:** 2026-11-03
- **Status:** accepted
- **Instructions:** [`docs/instructions/design.md`](../instructions/design.md) (Stack: production; V2 external databases);
  user in chat: "Is there a way we serve OFF entries ourselves? from the VPS. Batch downloading it", then "Option 2.
  I don't care if OFF doesn't run entirely on the device, that's one that can require internet no issue"
- **Supersedes:** [Server rate-limits its Open Food Facts searches](2026-10-26-off-rate-limit.md),
  [Open Food Facts: text search via search-a-licious](2026-10-17-off-search.md)

## Context

OFF was read live: text search through our `/off-search` relay to search-a-licious (10 searches a minute for all
users together, past which a 429), barcodes and products straight from each browser (15 reads a minute per IP), and
the legacy `cgi/search.pl` as fallback, mostly answering 503.

OFF publishes everything for bulk use (ODbL, same as the API):
- `openfoodfacts-products.jsonl.gz`, the full export, daily: 13.4 GB on 2026-11-02, ~25 KB of JSON per product.
- `delta/`: one file a day with the products changed that day (~20 MB, ~5k products), the last two weeks of them,
  listed in `delta/index.txt`.

Products in both are in OFF's nutrition schema since 2026 (`schema_version` 1004): no `nutriments`, but a
`nutrition.aggregated_set` of values per 100 g or 100 ml, already in g / kcal / kJ / % vol. Checked against the live
API for one product (6974913170331): its `<nutrient>_100g` are exactly those values. So the copy can hand the app
products in the API's shape, and `offDraft` / `offNutrients` stay as they are.

Two shapes were offered: an Argentina subset bundled like `fdc.json`, or the whole of OFF on the VPS. The user
picked the latter.

## Decision

- **`off/server.mjs`**, a third container (`deploy/off/Dockerfile`, compose service `off`, volume `off-data`), Node
  22 with its built-in `node:sqlite` (FTS5 included): no dependencies, like the backup server.
- **What's kept:** food products with values per 100 g/ml as sold, and of each only `OFF_FIELDS` (name, brands,
  quantities, serving, its `_100g` nutrients), the JSON deflated per row (half the size). Values OFF estimated from
  the ingredients (`source: estimate`, up to ~50 per product) are left out, as its API does, except added sugars,
  which the API gives. Prepared-food values (`preparation: prepared`) are left out, as the
  app never read `_prepared_100g`. Products with no usable values aren't stored: a barcode of one falls through to
  OFF itself, which gives what it has.
- **Full import** streams the export (download → gunzip → lines; lines without nutrition aren't parsed) into
  `off.new.sqlite`, fills the search index once at the end, then renames it over `off.sqlite`. Searches keep using the
  old copy meanwhile; only the very first import leaves nothing to serve (503).
- **Updates:** at start, then every 6 h. New deltas are applied in place, one transaction each, in order. A product
  is only replaced by a version at least as new (`last_modified_t`), so overlaps between the export and the deltas
  don't matter; the export counts as covering up to two days before its date (it's made over some hours). A full
  import runs again when there's no copy, when it's over 30 days old (`FULL_DAYS`: deletions on OFF only show up that
  way), or when deltas were missed (a gap in the two weeks OFF keeps).
- **Search:** FTS5 over the product's names in every language (`product_name_*`, so a Spanish name finds a product
  whose main name is French) and its brands, `unicode61` with diacritics removed. Every word must match the start of
  a word ("leche ent" finds "Leche entera"); one-letter words match whole. Ranked by bm25 (name ×3 over brand) minus
  0.5 × ln(1 + scans), so popular products come up among similar matches.
- **API**, in OFF's shapes: `/off/search?q=&page_size=` → `{hits}`, `/off/product/<code>` → `{status: 1, product}`
  (codes tried as typed, padded to 13 and unpadded), `/off/status` for checking on it.
- **The app** asks the copy first; picking a hit reads that product from the copy too. When the copy can't answer
  (down, still building, a static host) or doesn't have a barcode, it asks OFF directly as before; text then goes to
  `cgi/search.pl`. The "Max 10 searches per minute" line is gone. The service worker never caches `/off/`.
- **Removed:** the `/off-search` relay (Caddy and Vite) and the Caddy built with caddy-ratelimit; the web image is
  plain `caddy:2` again.
- **Development:** Vite relays `/off/` to production's copy (`OFF_COPY` to point it elsewhere, e.g. a local
  `off/server.mjs`).

## Alternatives considered

- **The Parquet export on Hugging Face, through DuckDB**: smaller download and column reads, but a dependency (a
  DuckDB binary or package) where streaming JSONL needs none. The deltas are JSONL anyway.
- **The CSV export** (~1 GB): flat, but no delta files in that format, so updates would mean re-downloading it.
- **Upserting the full import into the served file** instead of building a new one: no doubled disk during imports,
  but deletions need a mark-and-sweep, and the index is maintained row by row (slower).
- **Keeping search-a-licious as a fallback**: a second relay and its rate limit for when our own server is down,
  which is when the web app is likely down too.
- **Ranking by the user's country** (Argentine products first): there's no country setting; offered, not done.

## Consequences

- The VPS holds ~1.5 GB (~3 GB during a full import) and downloads 13 GB about once a month, plus ~20 MB a day. A
  full import is CPU-bound, one core: ~40 min here, maybe longer on the VPS.
- The first deploy takes a while to be useful: until the first import is done the app falls back to OFF directly
  (barcodes work; text search mostly doesn't).
- `deploy/server/compose.yaml` changed: it has to be copied to `/srv/track-shit` by hand (README), else the `off`
  service doesn't exist and `/off/` answers 502 (the app then falls back to OFF).
- ODbL: we serve a copy of a database under ODbL; the search screen already credits Open Food Facts and the licence.

## Verification

Against a local stand-in for `static.openfoodfacts.org/data`: the first 400k lines of the 2026-11-02 export (11 GB
uncompressed, ~27 KB a line, so the whole export is ~3.1 M products) and the last three real deltas.
- Full import: 5 min, 378,544 products kept (96% of lines); then the three deltas (17k products) applied in order,
  `deltas_until` at the last one's end. File: 172 MB for ~390k products (393 MB before deflating and dropping
  estimates).
- Search: "leche", "dulce de leche", "nutella", "coca cola", "yogur", "serenisima", "cafe" give sensible first hits
  in 2–30 ms; a lone "a" 90 ms; quotes and `*` in the query are harmless.
- Barcodes: as typed, 12-digit UPC (padded), 8-digit EAN; unknown → 404, letters → 400.
- Against OFF's live API (5 products): same names, brands, quantities, servings and `_100g` values; only its
  `fruits-vegetables-*-estimate-from-ingredients` (unused by the app) are missing.
- The app (Vite with `OFF_COPY` at the local copy, headless Chromium 412×915): a name search and a barcode lookup
  only call `/off/`, and picking Nutella prefills New food (package 400 g, nutrients). With the copy stopped, the
  barcode goes to OFF directly and still works.
- `npm run build`.
- Not checked: the Docker images and compose (no containers in the devcontainer), and a full 13 GB import. First
  real run is the deploy; `GET /off/status` shows its progress.
