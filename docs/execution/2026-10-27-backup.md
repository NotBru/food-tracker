# Encrypted backup: invite codes, one blob per public key, secret by QR link

- **Date:** 2026-10-27
- **Status:** accepted; two devices overwriting each other superseded by [sync](2026-10-28-sync.md)
- **Instructions:** [`docs/instructions/design.md`](../instructions/design.md) (Config screen; Production)
- **Builds on:** [Backup server direction](2026-10-26-backup-direction.md)

## Context

User in chat: "you upload a public key and that entitles you to store cyphertext with your database, and that's it.
Your browser keeps the private key, plus being able to share it via QR to another device (or copying the
plaintext). But I don't want people to use my storage for other shit." Options discussed: open with caps (proof of
work, trust that grows with age, per-blob download limits) or invite codes. User: "for now let's go with friends code".

## Decision

- **Secret**: 32 random bytes per backup, in `localStorage` (outside the database, so exports, imports and restores
  don't carry or clear it). HKDF-SHA-256 gives an Ed25519 seed and an AES-256-GCM key. The Ed25519 public key
  (base64url) is the backup's name on the server. All WebCrypto; no crypto library.
- **Blob**: `FTB1` + IV + AES-GCM(gzip(export JSON)). The export is the same as "Export databases" (whole device:
  all users, foods, config), so restore is `importAll` with its migrations.
- **Requests** are signed: `food-tracker-backup/1`, method, path, time, previous version, SHA-256 of the body.
  The server takes them within an hour of its clock. Uploads are compare-and-swap on the version the device last
  saw (409 otherwise), which also stops replays. Downloads are signed too, so only secret holders get the ciphertext.
- **Invite codes**: `node server.mjs invite <name>` makes a single-use code (16 random bytes). Registering a key
  uses one up (an atomic rename, so it can't be won twice). `list` and `remove <key>` for the rest. Lost secret =
  new code.
- **Limits**: one blob per key, replaced on each upload, at most 4 MB (`MAX_BYTES`). No expiry, no rate limits:
  every key is an invited person's.
- **Server**: `backup/server.mjs`, Node 22, no dependencies; one file per code, key and blob under `/data`, written by
  rename, so the CLI and the server never share a file. Image `deploy/backup/Dockerfile`, port 8080, runs as `node`.
  The web image's Caddy relays `/backup/*` to `$BACKUP_UPSTREAM` (default `backup:8080`): same origin, no CORS. The
  Vite dev/preview proxy sends `/backup` to `localhost:8787`. The service worker leaves `/backup/` alone.
- **App**: Config → Backup screen. Not set up: invite code → Start, or paste a secret/link → Restore. Set up: last
  backup, Back up now, Restore, Show secret (QR + text + Copy), restore from another secret, Forget the secret.
  - The QR holds a link, `…/#/backup?secret=…`: any phone camera opens it straight in the restore form. The hash
    never reaches the server, and the screen drops it from the address at once.
  - Automatic: 5 s after opening, every 15 minutes, and when the app goes to the background, if the data changed
    (hash of the export's tables). Stops on a conflict until the user picks Back up now (overwrite) or Restore.

## Alternatives considered

- **Bearer token instead of signatures** (server keeps a hash of it): simpler, but the user asked for a public key,
  and a logged token would allow writes; a logged signature allows nothing new.
- **@noble/ed25519**: Ed25519 is in WebCrypto in current Chrome, Firefox and Safari; old browsers get a message.
- **In-app QR scanner**: `BarcodeDetector` is missing in Firefox and iOS Safari; the phone's camera app already reads
  the link, and pasting covers computers.
- **Open registration with caps**: discussed; deferred by the user.
- **Sync** (merging two devices): out of scope; two devices on one secret overwrite each other, with a warning.

## How it was checked

- `npm run build`. Server and `vite preview` locally; headless Chromium (Playwright 1.55.0), two and three browser
  contexts as devices:
  - A wrong code is refused; a good one registers and uploads; reusing it fails.
  - A link opens the restore form with the secret filled and the address cleaned; restore asks, then replaces the
    data (an added user arrives on the other device).
  - Two devices on one secret: the second upload gets the conflict warning; Back up now overwrites.
- curl: forged signature 401, stale time 401, unknown key 404 before the body is read, over 4 MB 413.
- Not checked: `docker build` of either image and the Caddyfile (no containers, no Caddy in the devcontainer). First
  run is on the VPS. A real phone scanning the QR.

## Open questions

- The 4 MB cap is a guess (a year of logs should be a few hundred KB gzipped); worth checking against a real export.
- Changing the secret (if a QR leaks) needs a new invite code for now; a rotation signed by the old key would not.
  Done in [backup-rotate](2026-10-27-backup-rotate.md).
